# Assist Session Authentication

This document explains how the Assist server authenticates tracker (session) connections, how to configure it, and how to roll it out.

## Overview

Assist has two kinds of socket connections for a live session:

- **Agent** sockets, opened by the dashboard. These have always been authenticated with a JWT signed with `ASSIST_JWT_SECRET`.
- **Session** sockets, opened by `@openreplay/tracker-assist` in the end user's browser.

Session sockets now also have to prove they belong to the session they join. The tracker sends the session token it received from the backend when the session started, and the Assist server verifies it with `TOKEN_SECRET`, the same secret the ingestion services use to issue it. The session ID inside the token must match the session ID in the socket's `peerId`. Expired tokens are rejected, with the same 30-second grace period the backend uses.

In addition:

- Data sent by a session socket is relayed only to the agents connected to that session, not to other session sockets in the room.
- Events that only the server may emit (`NEW_AGENT`, `NO_AGENT`, `AGENT_DISCONNECTED`, `AGENTS_CONNECTED`, `AGENTS_INFO_CONNECTED`, `SESSION_DISCONNECTED`, `SESSION_ALREADY_CONNECTED`, `SESSION_RECONNECTED`, `WEBRTC_CONFIG`, `SERVER_UPDATE_SESSION`) are dropped when a session socket sends them.
- Connections with a missing or malformed `peerId`, or invalid `sessionInfo`/`agentInfo` JSON, are rejected or handled without affecting other connections.

## Environment Variables

These variables are read by the Assist server (`assist/`):

| Variable                       | Type    | Default | Description                                                                                                            |
| ------------------------------ | ------- | ------- | ---------------------------------------------------------------------------------------------------------------------- |
| `TOKEN_SECRET`                 | string  | none    | Secret used to verify tracker session tokens. Must be the same value the `http`, `images` and `canvases` services use. |
| `ASSIST_REQUIRE_SESSION_TOKEN` | boolean | `true`  | Set to `false` to accept session sockets without a token. Intended only for a staged rollout (see below).             |

If `ASSIST_REQUIRE_SESSION_TOKEN` is not `false` and `TOKEN_SECRET` is not set, the server refuses all session sockets and logs `TOKEN_SECRET is not set, refusing session sockets`.

## Configuration

### Helm

The Assist chart passes `TOKEN_SECRET` from the shared `token-secret` key of the OpenReplay secret (`global.tokenSecret`), the same value the ingestion services use. No extra configuration is needed.

To disable the check during a rollout, add the variable to the Assist chart's environment, for example:

```yaml
assist:
  env:
    ASSIST_REQUIRE_SESSION_TOKEN: "false"
```

### Docker Compose

`scripts/docker-compose/docker-envs/assist.env` sets:

```bash
TOKEN_SECRET="${COMMON_TOKEN_SECRET}"
```

`COMMON_TOKEN_SECRET` is generated by `install.sh`. If you upgraded an existing installation, check that `assist.env` contains the line above and that `common.env` does not still hold the `change_me_token_secret` placeholder:

```bash
grep TOKEN_SECRET docker-envs/assist.env
grep change_me common.env
```

To disable the check during a rollout, add `ASSIST_REQUIRE_SESSION_TOKEN="false"` to `docker-envs/assist.env` and recreate the container (`docker compose up -d assist`).

## Upgrading

Older versions of `@openreplay/tracker-assist` do not send a session token, so once the Assist server requires one, those trackers can no longer start Assist sessions. A newer tracker works with both old and new Assist servers, because older servers ignore the token.

Recommended order:

1. Deploy the new Assist server with `ASSIST_REQUIRE_SESSION_TOKEN=false`.
2. Release the updated `@openreplay/tracker-assist` in your web applications and wait for clients to pick it up (including cached bundles and long-lived tabs).
3. Remove `ASSIST_REQUIRE_SESSION_TOKEN` (or set it to `true`) and restart the Assist server.

If you deploy the tracker and the Assist server together, you can skip steps 1 and 3.

### Mobile SDKs

The iOS, Android and React Native SDKs are maintained in separate repositories and do not send a session token yet. If you use Assist with mobile apps, keep `ASSIST_REQUIRE_SESSION_TOKEN=false` until those SDKs support it.

## Troubleshooting

### Agents see "no sessions" / the end user never connects to Assist

Session sockets are being rejected. Check, in order:

1. The tracker uses an updated `@openreplay/tracker-assist`. When the token is missing or invalid, the `/ws-assist/socket` WebSocket opens but the server answers with a Socket.IO connect error, `Authentication error`, visible in the WebSocket's messages in the browser's network tab.
2. `TOKEN_SECRET` is set on the Assist server and matches the value used by the `http` service. A mismatch rejects every session socket.
3. The tracker has a session token. Assist starts after the tracker session starts. If the session failed to start, there is no token to send.

Run the Assist server with `debug=1` to log the reason for each rejected socket.

### Assist stopped working for long sessions

The session token expires when the session reaches the project's maximum session duration. After that, a reconnecting session socket is rejected. This matches the backend, which also stops accepting data for the session at that point.
